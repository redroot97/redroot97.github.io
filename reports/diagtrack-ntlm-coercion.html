diagtrack coercion

A standard domain user coerces the SYSTEM DiagTrack service into NTLM auth, relays it to the DC, and rides RBCD + Kerberos S4U to NT AUTHORITY\SYSTEM. CVE-2026-69267.

windows active directory privilege escalation ntlm coercion 2026.08
CVE-2026-69267  ·  Microsoft: Information Disclosure, Max Severity Important  ·  CWE-1220  ·  CVSS 3.1 6.5 (AV:L/AC:L/PR:L/UI:N/S:C/C:H/I:N/A:N)  ·  Windows 10 (all supported) & Windows 11 through Build 26200 (25H2), x64 + ARM64  ·  released Sep 8, 2026. MSRC advisory ↗
How to read this. Microsoft scored CVE-2026-69267 for its root cause: an unauthorized local caller reaching SYSTEM-context file-system access through the DiagTrack RPC method (information disclosure, CWE-1220). Everything below the coercion is what that primitive enables in a default Active Directory environment - the NTLM relay to NT AUTHORITY\SYSTEM - and it additionally depends on LDAP signing and channel binding not being enforced. That escalation chain is why the base score reflects disclosure rather than full EoP, and why any one of the LDAP-hardening controls below breaks it.

// the one-line version

The Windows Connected User Experiences and Telemetry service - DiagTrack, running as NT AUTHORITY\SYSTEM inside svchost.exe -k utcsvc - exposes an RPC method that takes a file path and accesses it as SYSTEM with no check on the caller. That unchecked SYSTEM-context access is the vulnerability Microsoft assigned the CVE to. Point the path at a WebDAV UNC and the SYSTEM context authenticates outbound with the machine account; relay that authentication to the domain controller, configure delegation against the machine's own AD object, and Kerberos hands you back an administrator. From a standard domain user with no admin rights, on localhost, in under 30 seconds.

// the vulnerable method

DiagTrack hosts an RPC interface with UUID 4c9dbf19-d39e-4bb9-90ee-8f7179b20283 (v1.0). Opnum 19 accepts a file-path parameter and accesses the target path in the SYSTEM security context - without verifying that the caller is elevated, without impersonating the caller, without any access check at all. Any authenticated principal with an interactive logon can invoke it.

That single missing check is the vulnerability. Everything after it is well-known NTLM-coercion and Resource-Based Constrained Delegation (RBCD) abuse - the novelty is that this primitive lives on a previously unreported RPC interface, in the same family as PetitPotam (MS-EFSR) and PrinterBug (MS-RPRN).

// step 1 - coerce SYSTEM into authenticating

DiagTrack registers its LRPC endpoint dynamically; the ALPC port name changes on every restart. The PoC resolves it at runtime with RpcEpResolveBinding over ncalrpc, then speaks LRPC by hand - a 72-byte bind message naming the DiagTrack UUID and NDR transfer syntax, followed by an Opnum 19 request whose body is an NDR-marshaled conformant string (the path) plus an 8-byte-aligned integer, delivered via NtAlpcConnectPort / NtAlpcSendWaitReceivePort. No RPC runtime stubs, no special token.

The path handed to Opnum 19 is a WebDAV UNC: 

\\127.0.0.1@<PORT>\DavWWWRoot\<random>.wprp

The server@port syntax forces the WebClient service (WebDAV Mini-Redirector) - not the SMB client - to service it. WebClient issues an HTTP request to 127.0.0.1:<PORT> and, when challenged, authenticates with NTLM using the machine account. Because DiagTrack runs as SYSTEM, that outbound auth carries the machine identity to a listener bound on loopback. Nothing crosses the network perimeter.

// step 2 - relay to LDAPS

NTLM isn't channel-bound by default, so the challenge/response captured over HTTP is replayed over LDAP. The PoC runs an HTTP listener and an LDAPS client to the DC as a cross-protocol relay:

SYSTEM WebClient -> attacker HTTP (127.0.0.1) DC (LDAPS 636) | | | HTTP 401 WWW-Authenticate: NTLM | | <- NTLM Type 1 (Negotiate) | | wrap in SPNEGO LDAP Bind -> | returns Type 2 (Challenge) | HTTP 401 WWW-Authenticate: NTLM <Type2> | | <- NTLM Type 3 (Authenticate) | | wrap in SPNEGO LDAP Bind -> | validates, bind completes | HTTP 200 OK | v v released authenticated LDAP session as MACHINE$

The machine hash never travels in clear, and default 120+ character machine passwords make cracking pointless. The value is the relay, not the hash - which is exactly why LDAP signing / channel binding are the killswitch: with either enforced, the relayed bind fails.

// step 3 - configure RBCD

With an LDAP session as MACHINE$:

  1. Create a computer object. ms-DS-MachineAccountQuota defaults to 10, so any authenticated principal can add one via LDAP Add (userAccountControl = 4096, an attacker-chosen unicodePwd, standard SPNs).
  2. Point the victim's delegation at it. LDAP Modify the victim's own object to set msDS-AllowedToActOnBehalfOfOtherIdentity to a security descriptor granting the new computer SID GenericAll. The machine account has write access to its own delegation attribute - so the relayed identity is sufficient.

// step 4 - Kerberos S4U to an admin ticket

The PoC implements Kerberos v5 from scratch (MD4, RC4, HMAC-MD5, ASN.1 DER):

  1. AS-REQ as the new computer account (RC4-HMAC) -> TGT.
  2. S4U2Self -> a ticket to the account itself impersonating Administrator (PA-FOR-USER, KerbChecksum, key usage 17).
  3. S4U2Proxy -> cifs/<victim-fqdn> using the S4U2Self ticket as the additional ticket (PA-PAC-OPTIONS RBCD flag, constrained-delegation KDC option).

Result: a cifs/<victim> service ticket that impersonates a domain administrator.

// step 5 - SYSTEM via SMB2 + SCM

That ticket is used against the local machine over SMB2 (SessionSetup via SPNEGO/AP-REQ, HMAC-SHA256 signing): TreeConnect to IPC$, open \pipe\svcctl, DCE/RPC bind to SCMR, then OpenSCManagerW -> CreateServiceW -> StartServiceW. Domain admins are local admins on domain members, so the SCM operations succeed - and the service starts as NT AUTHORITY\SYSTEM.

// why it stays quiet

  • No admin, no UAC, no token theft - the trigger is a plain RPC call from a standard user.
  • Localhost only - the coercion target is 127.0.0.1; nothing hits the perimeter.
  • Nothing on disk required - a single C# file compiles and runs in memory via the in-box compiler, no third-party libraries.
  • In testing it produced zero Windows Defender alerts, including with Tamper Protection on and Smart App Control in evaluation mode, on Windows 11 Build 26200 (25H2), x64 and ARM64.

// remediation

Vendor: add an RPC security callback to Opnum 19 requiring an elevated caller, and reject WebDAV/UNC paths in the path parameter.

Defenders, deployable today - any one of these breaks the chain:

  • Enforce LDAP signing (LDAPServerIntegrity = 2) and LDAP channel binding (EPA) - the most surgical fix; it kills the relay.
  • Set ms-DS-MachineAccountQuota = 0 to block the computer-object creation RBCD needs.
  • Disable the WebClient service on workstations that don't need WebDAV - removes the coercion.
  • Disable NTLM where feasible.

// detection ideas

  • WebClient (svchost) making outbound HTTP to loopback shortly after a DiagTrack RPC call.
  • A new computer object created in AD, immediately followed by an msDS-AllowedToActOnBehalfOfOtherIdentity write on a different machine object.
  • Kerberos 4769 for cifs/<host> where the requesting principal is a freshly created machine account (S4U2Self/S4U2Proxy).
  • Service creation (7045 / 4697) with an unusual ImagePath where the SCM caller authenticated over the network with a Kerberos ticket.
