ghost span c2

Hiding command-and-control traffic inside OpenTelemetry trace exports.

c2 red team opsec 2025.12

// the problem with C2 traffic

Every C2 framework has the same fundamental problem: getting traffic out of a monitored network without triggering alerts. Custom protocols get flagged. HTTP callbacks to unknown domains get caught by proxy inspection. DNS tunneling is slow and increasingly detected. Even HTTPS to cloud providers raises eyebrows when the SNI doesn't match expected patterns.

But there's one protocol that flows freely through enterprise networks, often explicitly whitelisted by security teams: OpenTelemetry.

// why OpenTelemetry

OpenTelemetry (OTel) is the industry standard for exporting traces, metrics, and logs from applications to observability backends like Datadog, Splunk, Grafana, and New Relic. The protocol, OTLP, runs over gRPC on port 4317 and HTTP on port 4318.

In any enterprise running modern microservices, OTLP traffic is expected infrastructure noise. Security teams whitelist it. Network monitoring tools classify it as legitimate. Proxy rules let it through. This makes it an ideal channel for C2 communication.

Key insight: OTLP trace exports are structured as nested spans with arbitrary key-value attributes. The protocol is designed to carry unstructured metadata. Commands and exfiltrated data fit naturally into span attributes without violating the protocol spec.

// how Ghost Span works

Ghost Span is a full C2 framework built around this idea. The implant communicates with the server by sending valid ExportTraceServiceRequest messages over OTLP/gRPC. To any network inspector, it looks like a normal application exporting traces to a collector.

architecture

[implant] [server] [operator] Go binary Python/FastAPI + grpcio Electron + React | | | |--- OTLP ExportTrace ----->| | | (beacon as spans) |--- stores in SQLite ----->| | | | | |<-- operator queues cmd ---| |<-- task in response ------| | | | | |--- result as spans ------>|--- displays output ------>| | (next beacon) | |

the beacon cycle

  1. The implant constructs a valid OTLP trace export with span attributes containing system info (hostname, user, PID, OS).
  2. It sends this as a standard ExportTraceServiceRequest to the server on port 4317 (gRPC) or 4318 (HTTP).
  3. The server parses the span attributes, extracts the beacon data, and stores it in SQLite.
  4. If the operator has queued a command, the server embeds it in the gRPC response metadata.
  5. The implant executes the command and sends the output as span attributes in the next beacon.

anti-sandbox triage gate

Before an implant is promoted to a full agent, it has to pass a triage gate: 2 successful beacons over a minimum of 30 seconds. This defeats automated sandboxes that detonate payloads for a few seconds and inspect network traffic. The implant stays dormant-looking until it's confirmed to be running on a real target.

// binary patching for config

The Go implant templates are compiled once and reused. Configuration (server address, callback interval, encryption keys) is injected at build time through binary placeholder patching - 128-byte {{PLACEHOLDER_X}} fields in the binary are overwritten with actual values. No recompilation needed per target. The operator desktop app handles this automatically. 

// placeholder in Go source (compiled into binary)
var serverAddr = "{{PLACEHOLDER_SERVER_ADDR________________________________}}"
var callbackInterval = "{{PLACEHOLDER_CALLBACK_INTERVAL________________________}}"

// at build time, binary search-and-replace fills these in:
// {{PLACEHOLDER_SERVER_ADDR___...}} -> "10.10.14.5:4317"

// what makes it hard to detect

  • Protocol compliance - traffic is valid OTLP. It will pass through any gRPC-aware proxy or OTel collector without errors.
  • Expected ports - gRPC on 4317, HTTP on 4318. These are standard OTel ports that are often pre-approved in firewall rules.
  • Legitimate TLS - the server generates valid TLS certificates. Traffic is encrypted end-to-end.
  • Blends with telemetry noise - in environments already running OTel, Ghost Span beacons are indistinguishable from real trace exports at the network layer.
  • No custom protocol markers - there are no magic bytes, custom headers, or unusual user-agent strings. Everything follows the OTLP spec.

// components

Server - Python FastAPI application with dual gRPC (port 4317) and HTTP (port 4318) listeners. Uses grpcio for OTLP message parsing. SQLite backend for agent tracking and task queuing. TLS with auto-generated certificates.

Desktop client - Electron application with a React frontend. Manages agents, queues commands, compiles and patches implant binaries. Embeds a Go 1.22 SDK and llvm-mingw for cross-compilation to Windows, Linux, and macOS from any platform.

Implant templates - Go binaries compiled for multiple OS/arch combinations. Templates include DLLs, shared objects, and standalone executables. Each template has placeholder fields that get patched with target-specific config at generation time.

// detection considerations

If you're on the blue side and want to detect this pattern:

  • Monitor for OTLP exports to destinations that aren't your authorized OTel collectors.
  • Inspect span attribute names and values for anomalies - real application traces have consistent attribute schemas, C2 beacons don't.
  • Correlate OTLP traffic sources against known instrumented services. A process sending OTel data that isn't in your service catalog is suspicious.
  • Watch for the triage pattern: exactly 2 short beacons followed by regular interval callbacks from a new source.
