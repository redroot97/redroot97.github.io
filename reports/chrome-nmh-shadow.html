nmh shadow attack

Hijacking Chrome extension communication by shadowing Native Messaging Host manifests.

macos persistence chrome 2026.04

// what are Native Messaging Hosts

Chrome extensions run in a sandboxed environment and can't directly interact with the operating system. When an extension needs to communicate with a native application - reading files, launching processes, accessing hardware - it uses Native Messaging. This is Chrome's official mechanism for extension-to-native-app IPC.

The bridge between the two is a Native Messaging Host (NMH) manifest: a JSON file that tells Chrome which binary to launch when an extension requests a native connection. Many enterprise tools use this pattern - endpoint agents, password managers, security software, and monitoring tools all register NMH manifests to communicate with their Chrome extensions.

// the resolution order problem

On macOS, Chrome looks for NMH manifests in two locations, in this order:

  1. User-level - ~/Library/Application Support/Google/Chrome/NativeMessagingHosts/
  2. System-level - /Library/Google/Chrome/NativeMessagingHosts/
Key insight: Chrome checks user-level first. If a manifest with the same name exists in both locations, the user-level manifest wins. This means any unprivileged user can shadow a system-level NMH manifest without modifying protected directories.

This is by design - Chrome intends for user-level manifests to override system-level ones. But from an attacker's perspective, this is a privilege-free hijack of trusted IPC channels.

// the attack flow

[Chrome Extension] | | "connect to com.example.nmh" v [Chrome NMH Resolution] | | 1. check ~/Library/.../NativeMessagingHosts/com.example.nmh.json | FOUND -> use this one (attacker's shadow manifest) | | 2. check /Library/.../NativeMessagingHosts/com.example.nmh.json | NEVER REACHED v [Attacker's Binary] <-- intercepts all NMH traffic | | logs messages, optionally proxies to real binary v [Real NMH Binary] <-- (optional) still processes normally

step by step

  1. Identify the target NMH - list manifests in /Library/Google/Chrome/NativeMessagingHosts/. Each .json file names a native messaging host used by an extension.
  2. Read the manifest - the JSON file contains the NMH name, path to the native binary, allowed extension IDs, and communication type (stdio).
  3. Create a shadow manifest - copy the manifest to the user-level directory (~/Library/Application Support/Google/Chrome/NativeMessagingHosts/), but change the path field to point to your binary.
  4. Drop the interceptor - place your binary at the path specified in the shadow manifest. This binary receives all messages the extension sends to the NMH.
  5. Proxy or replace - optionally forward messages to the real NMH binary so the extension continues to function normally while you capture everything in transit.

// what gets intercepted

The data flowing through NMH channels depends on the target. Common enterprise NMH use cases and what an attacker captures:

  • Endpoint management agents - device enrollment tokens, compliance status, MDM commands, security policy data.
  • Password managers - credential autofill requests, vault unlock events, saved login data being sent to the browser extension.
  • SSO/auth extensions - session tokens, SAML assertions, OAuth flows between the extension and the native SSO agent.
  • Security tools - DLP scan results, URL reputation lookups, browser isolation decisions.

// why this is dangerous

No privileges required. The user-level NMH directory is writable by the current user. No root, no admin, no TCC prompts, no entitlements. Any process running as the logged-in user can drop a shadow manifest.

No user interaction. The shadow takes effect the next time Chrome launches the NMH connection. The user sees nothing different - the extension works normally because the interceptor proxies traffic through.

Survives updates. Enterprise tools update their system-level manifests in /Library/. The user-level shadow in ~/Library/ is untouched by these updates and continues to take priority.

// targeting

To find targets on a given machine, enumerate existing system-level NMH manifests: 

ls /Library/Google/Chrome/NativeMessagingHosts/
# com.example.nmh.json
# com.vendor.agent.json

cat /Library/Google/Chrome/NativeMessagingHosts/com.example.nmh.json
# {
#   "name": "com.example.nmh",
#   "description": "Example NMH bridge",
#   "path": "/opt/example-agent/nmh-bridge",
#   "type": "stdio",
#   "allowed_origins": [
#     "chrome-extension://aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa/"
#   ]
# }

The POC takes configurable variables at the top of the Swift source - set the NMH name, extension ID, and real binary path to target any installed NMH.

// compile and run

# edit the target variables in nmh-shadow-poc.swift:
#   let nmhName = "com.example.nmh"
#   let extensionId = "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
#   let realBinary = "/opt/example-agent/nmh-bridge"

swiftc nmh-shadow-poc.swift -o nmh-shadow-poc
./nmh-shadow-poc

The POC creates the user-level directory if needed, drops the shadow manifest and interceptor binary, and demonstrates message capture. Restart Chrome (or the target extension) to activate the shadow.

// detection

  • Monitor the user-level NMH directory - any file creation in ~/Library/Application Support/Google/Chrome/NativeMessagingHosts/ should be investigated. Legitimate software installs to the system-level path.
  • Compare manifest sets - if the same NMH name exists at both user and system level, something is wrong.
  • Binary path validation - check that the path field in user-level manifests points to a signed, expected binary.
  • File system auditing - endpoint telemetry (EDR) should flag writes to the Chrome NMH directories.
