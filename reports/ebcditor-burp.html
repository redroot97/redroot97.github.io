EBCDitor

Pentesting IBM mainframes through Burp Suite with real-time EBCDIC decoding.

burp suite mainframe tooling 2024.06

// the mainframe problem

IBM mainframes still run the core infrastructure of most large banks, insurance companies, airlines, and government agencies. Despite their age, they process an enormous volume of critical transactions daily. And despite their importance, they are among the least-tested systems in any penetration testing engagement.

The reason is simple: mainframes don't speak the same language as modern tools. While the rest of the world uses ASCII (and UTF-8), IBM mainframes use EBCDIC - Extended Binary Coded Decimal Interchange Code. It's a completely different character encoding where the letter "A" is 0xC1 instead of 0x41, a space is 0x40 instead of 0x20, and nothing maps the way a pentester expects.

When you proxy mainframe traffic through Burp Suite, you see garbage. The request body is unreadable. The response is unreadable. You can't modify parameters, test for injection, or do anything useful because Burp doesn't understand EBCDIC.

// how mainframe access works

Enterprise users connect to mainframes through TN3270 terminal emulators. TN3270 is a variant of Telnet specifically designed for IBM 3270-series terminals. Modern web gateways often wrap this in HTTP/HTTPS, creating a web-accessible frontend to the mainframe.

[User's Browser] | | HTTPS (normal web traffic) v [TN3270 Web Gateway] | | translates HTTP <-> TN3270 | request bodies contain EBCDIC-encoded field data v [IBM Mainframe] | | processes transaction in EBCDIC | returns 3270 data stream v [TN3270 Web Gateway] | | wraps response in HTTP v [User's Browser] <-- renders as a terminal screen

The HTTP layer looks normal to Burp - valid headers, standard content types. But the request and response bodies contain EBCDIC-encoded data that represents mainframe screen fields, transaction codes, and user input. Without decoding this, a pentester is blind.

// what EBCDitor does

EBCDitor is a Burp Suite extension that sits in the proxy pipeline and provides real-time EBCDIC decoding, editing, and re-encoding. It adds a new tab to Burp's message editor that shows the EBCDIC content as readable ASCII, lets you modify it, and encodes it back to valid EBCDIC when you forward the request.

the workflow

  1. Intercept - Burp captures the HTTP request containing EBCDIC-encoded data in the body.
  2. Decode - the EBCDitor tab automatically detects and decodes EBCDIC fields to readable ASCII. You can now see transaction codes, user IDs, account numbers, and input fields.
  3. Edit - modify the decoded content directly in the editor tab. Test for SQL injection, transaction manipulation, access control bypass - the same attacks you'd run on any web application.
  4. Re-encode - when you forward the modified request, EBCDitor converts your ASCII edits back to valid EBCDIC before it hits the gateway.
  5. Inspect response - the response body is also decoded, so you can read the mainframe's output without switching to a hex editor.

// why this matters for pentesting

Without a tool like this, mainframe pentesting through a web gateway is effectively manual hex editing. You'd need to:

  • Copy the request body to a hex editor
  • Manually look up each EBCDIC byte in a conversion table
  • Figure out which bytes correspond to which screen fields
  • Make your changes in hex
  • Convert back to EBCDIC manually
  • Paste it back into Burp and forward

That process takes minutes per request. With EBCDitor, it's the same click-edit-forward workflow you use for any web application test. This turns mainframe pentesting from a painful manual exercise into something that moves at the same speed as regular web app testing.

// what you can test

Once you can read and modify the traffic, standard web application attacks apply to the mainframe layer:

  • Transaction ID manipulation - mainframe transactions are identified by short codes (like "CICS" transactions). Modify these to access unauthorized transactions.
  • Field overflow - 3270 screen fields have fixed lengths. Sending data beyond the field boundary can cause unexpected behavior on the mainframe side.
  • Access control testing - change user context fields, terminal IDs, or session tokens to test horizontal and vertical privilege escalation.
  • Input validation - test for command injection in mainframe input fields. EBCDIC-encoded payloads that wouldn't be caught by ASCII-based WAF rules.
  • Session handling - mainframe sessions work differently from web sessions. Test for session fixation, replay, and hijacking at the TN3270 layer.

// EBCDIC encoding reference

For context on what EBCDitor is translating, here are some common EBCDIC vs ASCII mappings: 

Character  ASCII  EBCDIC
---------  -----  ------
Space      0x20   0x40
A          0x41   0xC1
Z          0x5A   0xE9
0          0x30   0xF0
9          0x39   0xF9
@          0x40   0x7C
#          0x23   0x7B
$          0x24   0x5B

The mapping is non-linear and non-trivial - you can't just add an offset. EBCDIC groups letters into non-contiguous ranges (A-I, J-R, S-Z are in different blocks), which is why manual conversion is so painful and error-prone.

// installation

# build the extension JAR (requires Java + Gradle)
gradle build

# in Burp Suite:
# Extender -> Add -> select the built JAR
# the EBCDitor tab appears in the message editor

No external dependencies. The extension registers as a message editor tab and an HTTP listener. It activates automatically when it detects EBCDIC-encoded content in proxied traffic.
