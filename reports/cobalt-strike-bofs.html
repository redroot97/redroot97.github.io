sticky grabber BOF

Extracting credentials from Microsoft Sticky Notes via the SQLite WAL file, entirely in-process.

cobalt strike credential access bof 2024.09

// why sticky notes matter

People treat Microsoft Sticky Notes as a scratchpad. During engagements, these yellow squares consistently contain things that shouldn't be written down anywhere: passwords, API keys, BitLocker recovery keys, MFA backup codes, database connection strings, and internal URLs with embedded credentials.

Sticky Notes is a UWP application that ships with every Windows 10 and 11 installation. It syncs to the user's Microsoft account by default, which means the local database often contains notes spanning multiple devices. From a red team perspective, it's a high-value credential store hiding in plain sight.

Why not just open the database? The main plum.sqlite database is locked while Sticky Notes is running. But the SQLite Write-Ahead Log (plum.sqlite-wal) is readable without locking, and it contains all uncommitted writes - including note content that was typed and then deleted but hasn't been checkpointed yet.

// what is a BOF

A Beacon Object File is a small compiled C program that executes inside the Beacon process rather than spawning a new one. In a default Cobalt Strike configuration, running a command like shell whoami creates a new cmd.exe child process - an event that EDR tools flag immediately. A BOF runs entirely within the existing Beacon process: no new process, no fork-and-run, no suspicious parent-child relationships in the process tree.

BOFs use Cobalt Strike's Dynamic Function Resolution (DFR) to call Windows APIs. Instead of linking against DLLs at compile time, the BOF declares the functions it needs, and Beacon resolves them at runtime. The BOF's import table stays empty, which makes static analysis harder for detection tools.

// the target file

Sticky Notes stores its data in a SQLite database under the user's UWP app data directory: 

C:\Users\<username>\AppData\Local\Packages\
  Microsoft.MicrosoftStickyNotes_8wekyb3d8bbwe\
    LocalState\plum.sqlite-wal

The .wal file is the Write-Ahead Log. SQLite uses WAL mode to allow concurrent reads and writes. When a user creates or edits a note, the changes are first written to the WAL before being flushed (checkpointed) to the main database. This creates a window where the WAL contains data the main database doesn't - and critically, data that the user may have already deleted from the UI but that hasn't been purged from the log yet.

// how it works

[Operator Console] | | "inline-execute sticky_grabber.x64.o" v [Beacon Process] | | 1. GetUserNameA() -> resolves current username | 2. sprintf() -> builds path to plum.sqlite-wal | 3. OpenFile() -> opens WAL read-only (no lock) | 4. ReadFile() -> reads contents into memory | 5. filter loop -> strips NUL bytes, extracts text | 6. BeaconPrintf() -> sends readable output to operator | | all in-process, no child spawned v [Operator Console] <-- receives extracted note contents

step by step

  1. Resolve the username - calls ADVAPI32$GetUserNameA() to get the current Windows user. This avoids hard-coding paths and adapts to whichever user context the Beacon is running under.
  2. Build the file path - uses MSVCRT$sprintf() to interpolate the username into the full UWP package path to plum.sqlite-wal.
  3. Open the WAL file - calls KERNEL32$OpenFile() in read-only mode. The WAL file is not locked by Sticky Notes, so this succeeds even while the application is running.
  4. Read the contents - allocates a buffer and reads the WAL data using KERNEL32$ReadFile().
  5. Filter and extract - iterates through the raw bytes, stripping out NUL bytes. SQLite WAL files store text as UTF-16 with NUL padding between characters. Removing the NULs produces readable ASCII/UTF-8 strings.
  6. Return to operator - sends the filtered text back through BeaconPrintf(). The operator sees the raw note contents in the Cobalt Strike console.

// the Windows APIs

Every API call uses Cobalt Strike's dynamic import convention (LIBRARY$Function) to avoid touching the import table: 

// dynamic imports - resolved at runtime by Beacon
DECLSPEC_IMPORT BOOL   WINAPI ADVAPI32$GetUserNameA(LPSTR, LPDWORD);
DECLSPEC_IMPORT HFILE  WINAPI KERNEL32$OpenFile(LPCSTR, LPOFSTRUCT, UINT);
DECLSPEC_IMPORT BOOL   WINAPI KERNEL32$ReadFile(HANDLE, LPVOID, DWORD, LPDWORD, LPOVERLAPPED);
DECLSPEC_IMPORT BOOL   WINAPI KERNEL32$CloseHandle(HANDLE);
DECLSPEC_IMPORT void*  MSVCRT$malloc(size_t);
DECLSPEC_IMPORT void   MSVCRT$free(void*);
DECLSPEC_IMPORT int    MSVCRT$sprintf(char*, const char*, ...);

None of these APIs are inherently suspicious in isolation. GetUserNameA is called by thousands of legitimate applications. OpenFile and ReadFile are the most basic file I/O operations in Win32. This makes behavioral detection harder - the BOF's API call pattern looks like any application reading a file.

// what comes back

The output is raw text extracted from the WAL. In practice, this means a mix of SQLite internal structures, metadata, and the actual note contents. The useful data is scattered between formatting artifacts, but the operator can quickly grep through it for:

  • Passwords - users frequently paste credentials into Sticky Notes as a "temporary" reminder
  • API keys and tokens - AWS keys, Azure service principal secrets, GitHub PATs
  • Recovery codes - BitLocker recovery keys, MFA backup codes, password reset answers
  • Internal URLs - admin panels, internal dashboards, jump hosts with embedded credentials
  • Deleted content - notes the user removed from the UI but that still exist in the WAL

// OPSEC profile

The BOF has a favorable detection surface for red team operations:

  • No new process - runs entirely within the Beacon process. No cmd.exe, no powershell.exe, no notepad.exe with CreateRemoteThread. Zero process creation telemetry.
  • No DLL loading - all APIs are resolved dynamically through Beacon's existing loaded modules. No suspicious LoadLibrary calls.
  • No disk writes - the BOF reads data and sends it over the existing C2 channel. Nothing touches disk.
  • Normal file access pattern - reading files within the user's own AppData directory is routine behavior for thousands of applications.

The primary detection opportunity for defenders is monitoring file access to the Sticky Notes data directory. An EDR rule that alerts on non-UWP processes reading plum.sqlite-wal would catch this, though the access would appear to come from whatever process the Beacon is injected into.

// building and running

# compile (requires mingw-w64 cross-compiler)
cd Sticky_Grabber
make

# produces sticky_grabber.x64.o

# in Cobalt Strike beacon console:
beacon> inline-execute /path/to/sticky_grabber.x64.o

No arguments needed. The BOF auto-detects the current user and constructs the path automatically. Output streams directly to the operator console.
