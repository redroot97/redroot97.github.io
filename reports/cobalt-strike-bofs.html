cobalt strike BOFs

Custom Beacon Object Files for in-process execution during Active Directory engagements.

cobalt strike active directory bof 2024.09

// what are BOFs

Beacon Object Files (BOFs) are small compiled C programs that execute inside the Beacon process rather than spawning a new process. This is the critical difference between a BOF and a traditional Cobalt Strike post-exploitation module.

In a default Cobalt Strike configuration, running shell whoami creates a new cmd.exe process, which spawns a child process, which executes the command. That's three process creation events that EDR tools love to flag. A BOF that does the same thing runs entirely within the existing Beacon process - no new process, no fork-and-run, no suspicious parent-child relationships.

Why this matters: modern EDR solutions trigger on process creation telemetry. Cobalt Strike's default fork-and-run model for post-exploitation commands (like execute-assembly) is one of the most reliably detected patterns in enterprise environments. BOFs eliminate that entire detection surface.

// how BOFs work

A BOF is a compiled COFF (Common Object File Format) object file - the intermediate output of a C compiler before linking. Cobalt Strike's Beacon loads this object file into its own memory, resolves function imports dynamically, and calls the entry point. When the BOF finishes, Beacon frees the memory.

[Operator Console] | | "inline-execute myBof.o arg1 arg2" v [Beacon Process] (already running, already trusted by EDR) | | loads myBof.o into own memory | resolves imports via Beacon's Dynamic Function Resolution | calls go() entry point | | BOF runs IN-PROCESS | - calls Windows APIs directly | - output sent back via BeaconPrintf | - no child process spawned | | BOF returns, memory freed v [Operator Console] <-- receives output

the BOF API

BOFs use Cobalt Strike's Dynamic Function Resolution (DFR) to call Windows APIs. Instead of linking against DLLs at compile time, the BOF declares the functions it needs, and Beacon resolves them at runtime. This means the BOF's import table is empty - another feature that makes static analysis harder. 

// declare the Windows API function
DECLSPEC_IMPORT BOOL WINAPI ADVAPI32$LookupAccountSidW(
    LPCWSTR, PSID, LPWSTR, LPDWORD, LPWSTR, LPDWORD, PSID_NAME_USE
);

// call it like a normal function in go()
void go(char *args, int len) {
    ADVAPI32$LookupAccountSidW(NULL, pSid, name, &nameLen, domain, &domainLen, &use);
    BeaconPrintf(CALLBACK_OUTPUT, "Account: %S\\%S", domain, name);
}

// what's in the repo

This collection contains BOFs built for real Active Directory engagements. Each one targets a specific phase of the kill chain and is designed to minimize detection surface while maximizing operator efficiency.

AD enumeration

BOFs that query Active Directory without touching net.exe or dsquery.exe. Direct LDAP queries from within the Beacon process, formatted for operator readability. Covers user enumeration, group membership, GPO listing, trust relationships, and SPN discovery for Kerberoasting targets.

lateral movement

Alternatives to Cobalt Strike's built-in lateral movement commands (psexec, wmi, winrm) that avoid the default fork-and-run pattern. These BOFs perform the same operations - service creation, WMI method invocation, remote process execution - but in-process, with configurable parameters for evasion.

OPSEC tradecraft

Situational awareness BOFs for checking common detection tripwires before acting. Includes: listing AV/EDR products via WMI, checking PowerShell logging configuration, enumerating Sysmon rules, identifying honeypot accounts, and verifying whether specific API hooks are in place.

// why custom BOFs

Public BOF collections are widely available and widely signatured. Every popular open-source BOF repo has been analyzed by security vendors and has detections written for it. The value of custom BOFs is that they are unknown to detection engineering teams and AV signature databases.

  • Unique code patterns - public BOFs share common coding styles and API call sequences that get signatured. Custom BOFs use different approaches to the same operations.
  • Engagement-specific tuning - each BOF is written for a specific engagement context. No unnecessary functionality that broadens the detection surface.
  • Tested against target EDR - before deployment, each BOF is validated against the EDR stack present in the target environment.

// building

BOFs compile with x86_64-w64-mingw32-gcc (MinGW cross-compiler). Each BOF is a single C file with the Beacon API header: 

# compile a BOF
x86_64-w64-mingw32-gcc -c bof_source.c -o bof_source.o

# in Cobalt Strike console:
inline-execute /path/to/bof_source.o [arguments]

The repo includes a Makefile that builds all BOFs in one pass. Each BOF has a corresponding aggressor script (.cna) that registers it as a Beacon command with argument parsing and help text.

// detection perspective

BOFs are harder to detect than fork-and-run, but they're not invisible:

  • API call patterns - EDR tools with kernel-level API hooking can still see the calls, even though they come from the Beacon process rather than a child.
  • Memory scanning - the BOF code exists in Beacon's memory briefly. Memory scanning solutions can catch it during execution.
  • Network artifacts - LDAP queries, SMB connections, and WMI calls still generate network traffic regardless of how they're initiated.
  • Behavioral analytics - a process making LDAP enumeration queries followed by lateral movement attempts is suspicious regardless of whether it's using BOFs or traditional tools.
